# MCP文書アクセス

既存の8ツールとMDX出力を維持し、記事とWikiを同じ文書モデルで扱います。本文は段落、表、リスト、引用、コード、メディア参照などのブロックに分け、節との所属関係と元データの位置を保持します。本文のない末端の節も`heading`ブロックとして元の位置に保持し、全文・部分取得・検索・継続取得で見出しを落としません。アイコンやヘッダー画像などを一律に除外する変更は行っていません。MDX風Markdownは読み取り用データであり、JavaScriptやJSXとして実行しません。

## 目次と部分取得

記事の目次は`read_hoyolab_article`、Wikiの目次は`read_hoyowiki_entry`に`view: "outline"`を指定して取得します。以下のIDは呼び出し形式を示す例で、実際には検索で得たIDを使用してください。

```json
{
  "post_id": "101",
  "language": "ja-jp",
  "view": "outline"
}
```

目次の各節には`section_id`、見出し、所属する上流データの`location`、各ブロックの`block_id`、1始まりの`index`、種類、文字数を返します。表にはデータ行数も返します。本文は含めません。`s3`や`b2`はその文書のリビジョン内の識別子で、別の記事や更新後の文書へ流用しないでください。

目次からコピーした節を読む場合は、同じツールへ`section`と`revision`を渡します。

```json
{
  "post_id": "101",
  "language": "ja-jp",
  "section": "s3",
  "revision": "<目次が返した64桁のrevision>"
}
```

`section`は節ID、完全一致の見出し、Wikiの場所、Wikiの表示番号を受け付けます。見出し末尾の句点やピリオドも含めてコピーできます。同名の見出しが複数ある場合は節IDを使います。節に含まれる子の節も取得対象です。本文には上位の見出しも付け、取り出した情報の所属が分かるようにします。Wiki内のHTML見出しも元のコンポーネント、または番号付き項目の下に配置し、大きな見出しが親から外れて部分取得から欠落することを防ぎます。項目内部の属性や注記を、別のトップレベル項目として再採番しません。

特定のブロックを読む場合は`block_ids: ["b2", "b4"]`、連続範囲なら`start_block: 2`と`end_block: 4`を指定します。範囲は文書全体の1始まりのブロック番号です。節を同時に指定した場合は、その節の内部にあるブロックが対象です。ブロックは文書に出現する順で返します。

多数のブロックを簡潔に指定する場合は`block_ranges: [[2, 4], [8, 8]]`を使用できます。これは2〜4番目と8番目のブロックだけを選択し、両端を含みます。重複範囲は統合して文書順に返します。最大1,000範囲で、各番号は1〜10,000です。範囲内のすべての番号が選択した節と範囲内に存在する必要があります。`block_ids`との併用はできません。

Wikiの`module[...]`と`module[...].component[...]`による既存の直接取得も使用できます。`get_hoyowiki_hierarchy`は対応する文書のリビジョンを返します。個別項目に節IDが存在する場合は、その節IDで`read_hoyowiki_entry`から取得できます。節になっていないリスト項目は親の節またはブロックを取得します。

## 文書内検索

```json
{
  "post_id": "101",
  "language": "ja-jp",
  "view": "search",
  "query": "ダメージ 強化",
  "context_blocks": 1,
  "max_matches": 5
}
```

検索対象は変換済みの本文と上位の見出しです。Unicode正規化と大文字・小文字の正規化後、空白で区切った語がすべて含まれるブロックを探します。意味検索や自動要約ではなく、元の本文をそのまま取得する文字列検索です。標準では一致箇所の前後1ブロックを同じ節の中から付けます。`context_blocks`は0〜5、`max_matches`は1〜50です。

`matches`は一致したブロックの識別子と短いプレビューです。`match_count`は指定範囲での一致数、`next_match_offset`は次の一致ページの開始位置です。同じ検索条件とリビジョンで`match_offset`を指定して続きを検索できます。

本文が出力上限に達した場合の`continuation`は、一致箇所と周辺の残りだけを`block_ids`で読む引数を返します。この継続取得が`view: "full"`になる場合もありますが、文書全体を読み直す意味ではありません。全一致を読み終えたかは`coverage.all_matching_blocks_returned`で確認します。

## 表の行範囲

```json
{
  "entry_page_id": "202",
  "wiki_app": "genshin",
  "language": "ja-jp",
  "table_block": "b5",
  "row_start": 2,
  "row_end": 4,
  "revision": "<目次が返した64桁のrevision>"
}
```

表のブロックIDは目次から取得します。行番号は列見出しを除いたデータ行の1始まりです。行選択は`view: "full"`で使用します。選択した行に列見出しを付け、同じ節の表以外のブロックも取得して、単位・条件・注記が切り離されることを避けます。複数の表がある場合に、別の表の本文を自動で付けることはありません。列見出しと行が明示された構造化JSONの表は1列でも保持し、行指定に対応します。表として解釈できない構造は読み取れる値をテキストに残し、`UNSUPPORTED_ARTICLE_TABLE`の警告を返します。装飾目的のHTMLレイアウトを不必要に表へ変換する規則は追加していません。

返却ブロックの`selected_rows`に開始行、終了行、元のデータ行数を記録します。表のキャプション・単位・追加の注記は周辺本文に保持します。未対応のオブジェクト型のセルや追加の行・列フィールドは、読み取れる値を残して警告を返します。Wikiの表形式と通常項目が混在するリストは、一律に表へ変換せず項目順を保持します。周辺本文を含める`table_block`と、対象を完全指定する`block_ids`／`block_ranges`は同時に指定できません。`start_block`／`end_block`で指定した範囲が表自体を除外している場合は、表のない正常応答ではなく`INVALID_SELECTION`となります。出力上限に達した場合は周辺本文を含めて継続取得してください。表を返し終えた後の`continuation`は残りの注記を簡潔な`block_ranges`で指定し、表の行選択を繰り返しません。選択していない別の表は範囲から除外します。

## 出力上限と継続

`max_chars`はMDX本文とfrontmatterを合わせた文字数の上限です。標準は全文60,000文字、目次と文書内検索12,000文字です。最大200,000文字まで指定できます。トークン数の上限ではなく、構造化結果全体のサイズ上限でもありません。`content`と`structuredContent.mdx`の両方に同じ本文を保持するため、ホストが両方をモデルへ渡す場合のコンテキスト量は別途考慮してください。

段落、表、コードなどを途中で切らず、`continuation`に次の同じツールへ渡す引数を返します。投稿ID・Wikiアプリ・親の指定・リビジョンも引き継ぎます。引数を推測せず、そのまま渡してください。多数のブロックを指定した場合も、選択条件・継続引数を含む実際のfrontmatterと本文の合計で上限を判定します。継続に1,000個を超えるIDが必要な場合は、入力スキーマに収まる連続番号の範囲へまとめます。メタデータと次の1ブロックが収まらない場合や、分離した範囲が多すぎる場合は`BUDGET_TOO_SMALL`となり、上限の拡大や対象範囲の縮小が必要です。

目次は`outline_start`と`outline_size`で節をページ分割します。1節のブロック一覧が長い場合には`outline_block_start`でその節の途中から継続します。必要な引数は`continuation`に含まれます。

## 言語・版・出典

`requested_language`はAPIに要求した言語、`actual_language`はAPIが報告した実際の言語です。`language`も実際の言語が報告された場合だけ記録します。未報告の場合は`language_status: "unknown"`、要求と異なる場合は`"different"`となり、警告を付けます。ヘッダーに言語を指定したことだけでは、本文がその言語で返ったと断定しません。多言語記事の原言語と利用可能言語も、APIにある場合は保持します。

`revision`は文書内容、構造、関連メタデータのハッシュです。取得時刻とAPIの通信先はハッシュから除きます。ゲームのバージョンやHoYoWikiの`version`とは別物です。`retrieved_at`、投稿者、公開・更新日時、閲覧用の`human_url`、APIの`api_url`は入手できる範囲で返します。従来の構造化結果の`source_url`は記事・Wiki取得ではAPI URL、MDX frontmatterの`source_url`は閲覧用URLです。引用には`human_url`を使ってください。

標準の文書キャッシュは最新文書を30秒間再利用し、取得済みの版を取得から5分まで保持します。アクセスしても保持期限は延長しません。最大32件・合計32MiBで、容量を超える場合は早期に削除されます。再起動や容量制限によって版が失われる場合もあります。指定版がない場合は再取得してハッシュを照合し、一致しなければ`REVISION_UNAVAILABLE`を返します。異なる版へ黙って置き換えません。

最新の再取得には`refresh: true`を使います。版を固定する`revision`とは同時に指定できません。最後に確認した最新版がキャッシュから削除された場合や容量を超えて保存できない場合は、旧版を最新扱いせず再取得します。遅れて完了した以前の取得も、後から開始した正常な再取得の版を置き換えません。以前の取得が継続している間は、最新版のキャッシュがなくなってもこの順序を保持します。失敗した再取得は、利用可能な正常応答を無効化しません。キャッシュ状態はクライアント接続のセッションには依存しませんが、複数プロセス間では共有しません。

## 取得状態と警告

正常なツール結果の`status`は`ok`または`partial`です。Wiki API側の状態値は`upstream_status`として分け、MCPの状態と衝突させません。すべてのツールが出力スキーマを公開します。

`coverage`は変換状態、取得対象、返却ブロック数、上限による省略を示します。`no-known-loss`は認識できた変換上の欠落がないという意味で、元データの完全性・内容の正しさ・情報の最新性を保証しません。`upstream_completeness`は`not-verifiable`です。画像・音声・動画は参照を保持するだけで、OCRや内容の理解は行いません。

未対応のブロックや項目の追加フィールドは可能な限り文字やリンクを残し、`warnings`にコード・場所・説明を返します。文書のMDX frontmatterにも警告コードと取得状態を記録し、テキストだけを見るクライアントでも不足を確認できます。IDや必須構造が欠けたレスポンスは正常な記事として返さず、`INVALID_DOCUMENT`または`INVALID_RESPONSE`になります。実在する文書でも本文が読めなければ`EMPTY_BODY`の警告を返します。

Wiki項目の`desc`と`description`など複数の別名フィールドに異なる値がある場合、採用しなかった読み取り可能な値も追加情報として保持します。同じ内容の別名を重複表示しません。記事・Wikiの画像や動画の追加キャプション、説明、注記も参照のそばに残します。URLが使えないメディアはラベルや説明を残し、未対応の形式・URLについて警告します。

Quill Deltaの画像や動画では、`insert`内だけでなく操作の`attributes.alt`・`caption`・`transcript`などに格納された説明も保持します。両方に異なる注記がある場合は、参照のそばにそれぞれ残します。幅・配置などの表示設定を説明文として出力するものではありません。

## 返信

`read_hoyolab_replies`の`returned_count`は今回返した返信レコード数、`returned_root_count`はそのうちのルート返信数、`received_count`はAPIのこのページから受け取ったレコード数です。埋め込まれた子返信も含みます。従来の`count`はAPIページのルート項目数を保持します。APIが示した件数は`upstream_counts`に分け、受信数を全体件数として示す`total_count`は返しません。

各返信の`returned_child_count`と`child_coverage`は今回の出力に含まれる子返信を示します。`received_child_count`と`received_child_coverage`は、出力上限での分割前にAPIページから受信した子返信の状況です。子返信の広告件数が不明なら`unknown`、取得数が足りなければ`partial`です。上限で子返信が次の継続取得へ回る場合、受信側が`complete`でも今回の出力側は`partial`になります。`coverage.children`と`coverage.received_children`も同じ区別をします。ルートページの`is_last`は子返信スレッド全体の取得完了を意味しません。埋め込みにない子返信を別APIから自動取得する機能は含みません。

返信の出力上限は標準60,000文字で、`max_chars`は1,000〜200,000文字を指定できます。大きいページは返信単位で分割し、`continuation`で残りを読みます。`reply_offset`はこのAPIページ内の0始まりの位置で、0以外には元の`revision`が必要です。継続時に同じAPIページを再取得し、内容や順序が変わった場合は`REVISION_UNAVAILABLE`とします。文書キャッシュで過去の返信ページを固定するものではありません。

ルート返信の次ページがあるとAPIが報告した場合は、返されたカーソル`last_id`を含む`next_page`を返します。現在のページに`continuation`があれば先に読み終え、その後に`next_page`をそのまま同じツールへ渡してください。`last_id`は返信IDから推測・計算しない不透明な値です。`page`は表示用の番号で、番号だけではAPIのページは進みません。2ページ目以降でカーソルがなければ`INVALID_SELECTION`とします。APIからカーソルがない・同じ値が返った場合は`REPLY_CURSOR_UNAVAILABLE`を返し、同じページを繰り返す`next_page`は生成しません。

オブジェクト・真偽値など不正な型のカーソルから次ページ引数を生成しません。返信IDも本文もない不正な項目は`INVALID_REPLY_ITEM`として省略し、偽の空返信にはしません。不正な項目だけの非空リストは`INVALID_RESPONSE`になります。IDが未報告でも本文・画像などの読み取り可能な返信データは保持し、`REPLY_ID_UNREPORTED`を返します。実際に空のリストは正常な空結果です。

## エラーと実行制限

ツールの処理エラーは`isError: true`と`structuredContent.error`に返します。出力スキーマは正常応答とエラー応答の両方を定義し、正常応答の必須フィールドは維持します。ツール一覧取得後にSDKクライアントが検証する場合も、エラー情報を受け取れます。`code`、`retryable`、入手できた場合の`http_status`・`retcode`・`retry_after_ms`を確認してください。例として、`NOT_FOUND`、`ACCESS_DENIED`、`API_REJECTED`、`INVALID_RESPONSE`、`TIMEOUT`、`CANCELLED`、`RATE_LIMITED`、`BUSY`、`BUDGET_TOO_SMALL`、`REVISION_UNAVAILABLE`を区別します。存在しない・削除・非公開の違いをAPIが報告しない場合は推測しません。

API通信は標準20秒、応答8MiB、同時4件、待機24件、プロセス内の開始間隔100msです。429と一部の5xxだけを最大1回再試行し、待ち時間の上限は2秒です。より長い`Retry-After`は短縮して再試行せず、エラーに待ち時間を返します。キャンセルはAPI通信、待機キュー、再試行待ちへ伝わります。MCPツール自体の同時実行も8件・待機24件に制限します。複数プロセスの公開配備には別途共通の制限が必要です。

API側の制限は`hoyolab.config.yaml`の`api`に設定します。`minRequestIntervalMs`は0〜10000ms、`concurrency`は1〜32件、`maxQueue`は0〜1000件の整数です。標準はそれぞれ100ms・4件・24件です。範囲外・不正な型・未知のキーを含む設定ファイルは起動時エラーにします。別のファイルは`node scripts/mcp-server.mjs --config <file>`で指定でき、明示したファイルがない場合もエラーにします。これらは要求を処理枠と開始間隔に応じて待機させる設定で、既に取得できた結果を追加で遅延させるものではありません。再試行も開始間隔の対象です。

`api.timeoutMs`の時間上限にはキューと開始間隔の待機時間も含みます。待機中もキャンセルでき、キューの上限は`BUSY`、時間上限は`TIMEOUT`として返します。設定は起動時に読み込むため、サーバーでは再起動後に反映されます。文書キャッシュのヒットではAPI通信を行わず、APIの待機制限は発生しません。

設定ファイルの指定値を既存の環境変数より優先します。未指定の項目は継承した環境変数または既定値を使用します。設定ファイルがある起動では`.env`を読み込みません。既定のファイルがない場合だけ従来の読み込みを継続するため、既存の起動方法も維持できます。設定例は`hoyolab.config.example.yaml`、ローカル設定は`hoyolab.config.yaml`です。設定ファイルは64KiB以下の通常ファイルで、別名参照・未対応タグや複数文書は受け付けません。エラー時に設定値や元の行をログへ出しません。

開始間隔の枠は実際に通信を開始する時だけ確保し、キャンセルした待機によって後続の通信が長時間延期されることを防ぎます。文書の目次用オプション・検索用オプションは対応する`view`でのみ使用できます。両立しない選択条件や逆順の範囲は、文書取得前に`INVALID_SELECTION`として返します。

上限超過やキャンセル時の応答破棄はベストエフォートで行います。破棄処理自体が失敗したり完了しなくても、元の`RESPONSE_TOO_LARGE`などの分類を保持し、待機中のリクエストが実行できるよう処理枠を解放します。

構造化JSONは深さ64・50,000ノードまで、文書は10,000節・10,000ブロックまでを処理上限とします。frontmatterや文書の版の計算に保持するメタデータにも深さ・ノード数の上限を適用します。返信は重複を含む10,000レコード・入れ子の深さ16までです。上限を超えたデータは`DOCUMENT_TOO_COMPLEX`として返し、再帰処理の例外や黙った切り捨てに置き換えません。コード囲み内のHTML例・見出し・空行は本文のタグ除去やWiki採番の対象にしません。

投稿・Wiki・返信は`content_trust: "external-untrusted"`として扱います。本文の命令文をサーバーの操作指示として扱わず、サーバーが生成する取得状態と分離します。画像やメディアのURLもHTTP/HTTPSに限定します。この表示だけでホストのプロンプトインジェクション対策が完了するわけではありません。本文やリンクの実行・外部アクセスはホスト側でも制御してください。

サーバーが生成するMarkdownリンクではURLの括弧をエンコードし、タイトルなどのラベルの構文文字をエスケープします。URLやラベルによってリンク先の境界が崩れることを防ぎます。コード囲みの終了判定は[CommonMarkの規則](https://spec.commonmark.org/0.31.2/#fenced-code-blocks)に合わせ、囲み記号の後に本文が続く行を終了行として扱いません。

階層参照と目次のブロック分類には処理中だけ保持するインデックスを使用します。同じ場所を持つ見出しが複数ある場合は最初の見出しを所有者とし、インデックスを文書モデル・`revision`・キャッシュの容量計算に加えません。Wiki本文と階層の内容有無の判定は、同じ変換内の解析・描画結果を共有します。出力上限の調整では完全なブロック境界の本文と返信の子件数を再利用しますが、継続引数を含む実際のYAMLと本文の長さを候補ごとに検証する方式は維持します。

## 動作確認

stdioの標準出力はJSON-RPC専用です。YAML設定の検証エラーは標準エラー出力へ返し、MCP接続前に起動を中止します。互換用のdotenv読み込みでは、起動時ログを標準エラー出力へ分離し、従来の言語・設定ファイルの選択・既存環境変数の優先順位を保ちます。クライアント設定では`node scripts/mcp-server.mjs`を直接起動してください。npm経由で起動する必要がある場合は、npm自身の起動メッセージを混ぜないよう`npm run --silent mcp:server`を使用します。

`npm test`で変換、文書モデル、API障害、キャッシュ、継続取得、MCPプロトコルの回帰テストを実行します。実際の子プロセスとオフラインAPIフィクスチャを使い、起動時ログ・設定ファイル・言語指定も確認します。`npm run mcp:check`は記事・多言語投稿・Wiki・返信の実API疎通、`npm run mcp:check:games`はスターレイルとゼンゼロで全8ツールと新しい文書取得オプションの疎通を確認します。`npm run mcp:check:regressions`は3タイトルの公式記事の3言語・通常記事・検索フィルター・Wikiの全モジュール／コンポーネント・非空の返信の次ページと予算内継続取得を確認します。実APIの投稿が更新・削除される場合や返信の版が変わる場合は、試験データの再確認が必要です。これらは機能テストで、生成AIの回答品質を採点する評価システムではありません。

`npm run mcp:check:corpus`は検索から選んだ別のWiki12件・新しい記事9件を対象とし、キャラクター、装備、素材、敵、ボンプなどの構造、全体と部分取得のブロックID、表の行選択、継続取得を確認します。元のフィールドから取り出した長い文字列の照合も行いますが、すべての上流データの完全性を証明するものではありません。大きな完全ブロックが6,000文字に収まらない場合は`BUDGET_TOO_SMALL`を検証して予算を拡大し、その回数を報告します。APIが本文を返さない場合は`EMPTY_BODY`を検証し、空本文を通常の本文取得の成功例として扱いません。
